# Go 后端开发规范

本规范适用于 `app/` 下 Go 控制面代码。当前后端入口为 `app/cmd/server/main.go`，通过 `server.InitializeApp()` 组装配置、日志、数据库、Redis、JWT、WebSocket、Router、Asynq Worker/Scheduler，并由 `app.Run()` 管理生命周期。

## 1. 项目边界与技术栈

- Go 版本以 `app/go.mod` 为准，当前为 `go 1.26.0`。
- Web 框架使用 Gin，ORM 使用 GORM，数据库默认 PostgreSQL，缓存/队列使用 Redis + Asynq。
- 依赖注入使用 Google Wire，应用层入口在 `app/internal/server/`，路由业务层入口在 `app/internal/router/`。
- 业务分层保持单向依赖：`Handler → Service → Repository → Model`。
- C++ 推理引擎、MQTT/HTTP 通信、FlatBuffers 消息转换与算法包不写在 Go 业务分层中，Go 侧只保留控制面、任务调度、协议适配和结果落库职责。

## 2. 目录职责

- `cmd/server/`：HTTP 服务入口。
- `cmd/migrate/`：数据库迁移、扩展初始化和种子数据。
- `cmd/gen/`：CRUD 代码生成器入口。
- `internal/handler/`：参数绑定、校验、调用 Service、返回统一响应，禁止业务逻辑。
- `internal/service/`：业务规则、事务编排、权限补充校验、跨仓储协调。
- `internal/repository/`：GORM 数据访问，禁止混入业务判断。
- `internal/model/`：GORM Model 定义。
- `internal/dto/`：请求/响应 DTO，必须使用 `validate` tag 表达入参约束。
- `internal/middleware/`：Recovery、Logger、I18n、CORS、RateLimit、Auth、RBAC、Audit、ZLM Webhook 等中间件。
- `internal/pkg/`：JWT、hash、errors、response、validator、i18n、ws、ipc、zlm 等内部基础设施。
- `internal/task/`：Asynq worker、scheduler 与后台任务 handler。
- `pkg/storage/`：local、PG large object、S3/OSS 兼容存储抽象。
- `pkg/gen/`：CRUD 代码生成器与模板。

## 3. Context 传播

- Handler 从 `c.Request.Context()` 获取请求上下文，并传递给 Service。
- Service 方法接收 `ctx context.Context` 作为第一个参数，并继续传递给 Repository 和外部调用。
- Repository 方法接收 `ctx context.Context` 作为第一个参数，数据库操作必须使用 `db.WithContext(ctx)`。
- Service、Repository、Handler 禁止用 `context.Background()` 替代请求上下文。
- 允许使用 `context.Background()` 的场景仅限进程级启动/关闭、Asynq 后台任务根上下文、CLI、测试、无请求上下文的 SDK 初始化或缓存预热。
- goroutine 必须有明确生命周期，优先使用 `errgroup`、`sync.WaitGroup` 或可取消 context 管理。

## 4. 错误处理与响应

- 所有错误必须显式处理，禁止用 `_` 忽略关键错误。
- 外层包装错误使用 `fmt.Errorf("%w", err)`，保留错误链。
- 业务错误统一使用 `internal/pkg/errors` 的错误码与构造函数。
- HTTP 输出统一使用 `internal/pkg/response`，成功用 `response.OK` / `response.Page`，失败用 `response.Err` 或通过 `c.Error(err)` 交给错误中间件。
- API 不能把原始数据库错误、SDK 错误、panic 文本直接返回给前端；面向用户展示的信息必须经过后端 i18n 翻译。
- Recovery 负责兜底 panic，内部错误码以 `internal/pkg/errors` 实际定义为准，当前内部错误为 `ErrInternal = 50001`。
- Auth、RBAC、RateLimit、ZLM Webhook 等协议边界中间件允许直接中止请求，但响应格式仍必须保持项目统一结构或第三方协议要求。

### 响应 JSON 格式

统一响应结构：

- 成功：`response.OK(c, data)` → `{ "code": 0, "message": "success", "data": {} }`
- 错误：`response.Err(c, errors.New(code, message))` → `{ "code": 10001, "message": "错误信息" }`
- 分页：`response.Page(c, list, total, page, pageSize)` → `{ "code": 0, "message": "success", "data": { "list": [], "total": 100, "page": 1, "page_size": 20 } }`

## 5. i18n 与展示文本

- 所有返回给前端并可能展示给用户的错误、提示、状态说明都必须支持 i18n。
- Handler 和 Service 不硬编码面向用户的错误句子；应返回错误码、翻译 key 或项目统一错误对象。
- 新增错误码时必须同步翻译资源，至少覆盖简体中文、繁体中文、英语；已有前端支持语言还包括印尼语、日语、韩语时应同步补齐。

## 6. Wire 依赖注入

- 新增 Repository、Service、Handler 或基础设施 provider 时，必须修改对应 `deps.go` / `wire.go`。
- 应用级依赖放在 `internal/server/`，路由业务依赖放在 `internal/router/`。
- 禁止手动修改 `wire_gen.go`；生成文件只通过 `make wire` 更新。
- 禁止绕过 Wire 在路由注册处临时 `new` 业务依赖。
- 接口绑定使用 `wire.Bind(new(Interface), new(*Impl))`，接口定义优先放在使用方。

## 7. 数据库与事务

- Repository 只负责数据访问，不做权限、状态机、跨资源业务判断。
- 事务由 Service 层编排，事务内所有 Repository 调用必须共享同一个 `ctx` 与事务 DB。
- 数据查询使用 GORM 参数化能力，禁止拼接用户输入到原生 SQL。
- 迁移逻辑保持幂等，新增模型后同步 `cmd/migrate`、测试数据与必要索引。
- 涉及 pgvector、JSONB、FlatBuffers 结果映射时，应定义清晰 DTO/转换层，避免在 Handler 内拼装。

## 8. 安全与日志

- 密码必须使用 bcrypt，cost 以项目实现为准，当前为 12。
- JWT secret、数据库密码、对象存储密钥等只通过环境变量或安全配置注入，禁止写入仓库。
- 日志使用 `zap.L()` 或注入 logger，禁止 `fmt.Println`、`log.Println` 输出业务日志。
- 日志中禁止出现密码、Token、Refresh Token、对象存储密钥、完整身份证件号等敏感信息。
- 文件上传必须校验大小、MIME、扩展名、路径穿越和存储后端错误。
- 密钥（JWT_SECRET、数据库密码、对象存储密钥等）仅通过环境变量注入，禁止出现在配置文件或版本控制中。

### 配置加载

配置加载优先级：**环境变量 > .env > config.yaml > 默认值**。

所有项目环境变量统一使用 `NIKO_` 前缀，避免与系统或其他应用冲突。密钥类配置必须仅通过环境变量注入，不得写入配置文件或硬编码。

## 9. Swagger 与 API 约定

- 新增或修改 Handler 时必须同步 Swagger 注解。
- API 路径统一挂载在 `/api/v1` 下，除健康检查、Swagger、静态资源或第三方 webhook 特例外不得另起风格。
- 请求体、查询参数和路径参数必须通过 DTO 或明确绑定结构体校验。
- 分页响应使用项目统一分页结构，字段命名保持 snake_case JSON 风格。

## 10. 测试与验证

- 测试文件命名为 `*_test.go`，优先写表驱动测试。
- 覆盖率目标为 `>= 70%`，以项目根规范为准。
- 修改业务逻辑后优先运行聚焦测试，再运行全量测试。
- 常用命令：
  - `cd app && make unit-test`
  - `cd app && make lint`
  - `cd app && make build`
  - `cd app && make wire`
  - `cd app && make swag`
  - `cd app && make integration-test` (Docker Compose 编排本地 PostgreSQL + Redis + ZLMediaKit + Engine 全链路集成验证)

## 11. 代码生成

- CRUD 生成器生成 Handler、Service、Repository、Router、DTO 时，不要手动破坏生成模板约定。
- 修改生成模板后必须验证至少一个目标模型的生成结果。
- 生成文件头部保留 `Code generated by niko-admin. DO NOT EDIT.` 语义，不在生成文件内做长期手改。

### 文件头模板

代码生成器生成的文件必须包含以下头部：

```go
// Code generated by niko-admin. DO NOT EDIT.
// Model: internal/model/user.go
// Generate at: 2026-05-15 10:00:00
```

禁止手动在生成文件内长期修改代码；需要持续定制的部分应提取到独立文件。
